## 一、品牌核心訊息

```
輕鬆感 · 自由感 · 放空感
```

- 所有 UI 設計圍繞這三個關鍵詞展開
- 不花巧、無需動畫、無需漸變色
- 風格統一性：元素元件、字體、按鈕、色彩、圖標保持一致

## 二、品牌視覺設計風格

### 2.1 品牌視覺元素
- **SVG 插圖**: 全域網站使用具設計感的 SVG 插圖，畫風為手繪趣味性風格，帶出品牌訊息
- **黑色主題背景**: 全域為黑色 theme 背景，加強所有咖啡產品的視覺對比
- **背景裝飾**: 大多數頁面背景有透明度低的 SVG 插畫元素，附有 CSS 動畫 `noise_animation`，豐富視覺層次

### 2.2 產品照片
- 所有咖啡和咖啡豆使用**無顏色背景的 PNG 去背圖**，僅呈現產品物件本身
- 去背圖加強產品視覺焦點，讓顧客專注於產品本身

### 2.3 咖啡杯及咖啡豆包裝設計
- **設計統一性**: 所有包裝設計保持一致風格，營造獨有品牌感
- **插畫風格**: 每個包裝均帶有不同的插畫，畫風傳達「輕鬆感、自由感、放空感」
- **口味配色**: 每種咖啡及咖啡豆口味都以不同的顏色設計，便於識別

### 2.4 動畫視覺元素

#### 2.4.1 SVG 背景插畫 + noise_animation
頁面背景使用透明度低的 SVG 插畫元素，搭配 CSS `noise_animation` 動畫，豐富視覺層次。

**技術實現**:
- CSS class: `.noise_animation` — 使用 `desktop_noise_animation` 關鍵幀動畫，1 秒循環，`will-change: filter`
- CSS class: `.noise-filiter` — 隱藏的 SVG filter 容器（`display: none; width: 0; height: 0`）
- CSS class: `.smart_noise_animation` — 行動裝置優化版本
- 關鍵幀 `@keyframes desktop_noise_animation` — 透過 SVG noise filter（`#noise-0` ~ `#noise-4`）產生噪點抖動效果
- 關鍵幀 `@keyframes smart_noise_animation` — 行動版（`#noise-5` ~ `#noise-9`）

**使用範例**:
```html
<!-- 頁面 banner 背景 SVG 插畫 + noise_animation -->
<div class="ftco-subpage-banner" id="section-counter">
    <div class="svg-bg ftco-counter noise_animation" 
         style="background-image: url({% static 'images/title_bg_img_01.svg' %});"></div>
    <div class="container">
        ...
    </div>
</div>

<!-- 商品卡片 hover 效果 -->
<span id="svg_over_on">
    <img src="{% static 'images/product_hover.svg' %}" class="noise_animation">
</span>

<!-- 首頁裝飾元素 -->
<div class="noise-img">
    <img src="{% static 'images/owl_title_bg_01.svg' %}" class="noise_animation">
</div>
<div class="svg-box">
    <img src="{% static 'images/owl_title_bg_02.svg' %}" class="noise_animation">
</div>
```

**應用頁面**:
| 頁面 | SVG 插畫 | 用途 |
|------|----------|------|
| 首頁 (`index.html`) | `owl_title_bg_01.svg`, `owl_title_bg_02.svg`, `product_hover.svg` | 背景裝飾、商品 hover |
| 咖啡菜單 (`coffee_menu.html`) | `title_bg_img_01.svg`, `product_hover.svg` | Banner 背景、商品 hover |
| 咖啡豆菜單 (`bean_menu.html`) | `title_bg_img_02.svg`, `product_hover.svg` | Banner 背景、商品 hover |
| 全域 (`base.html`) | — | noise-filiter SVG filter 容器 |

#### 2.4.2 背景訊息字體元素（title-bg-head）
頁面背景使用透明度極低的品牌字體元素，與頁面內容相關，豐富視覺層次。

**技術實現**:
- CSS class: `.title-bg-head`
  - `font-family: 'Mogra'` — 使用品牌 Logo 字型
  - `font-size: 20vw` — 超大尺寸
  - `opacity: .05` — 極低透明度
  - `position: absolute; z-index: -2` — 置於背景層
  - `letter-spacing: -10px` — 緊湊字距
  - `color: #fff` — 白色文字

**使用範例**:
```html
<!-- 咖啡商品詳情頁 -->
<span class="title-bg-head">｛BREWED<br>&nbsp;&nbsp;&nbsp;FAST｝</span>

<!-- 咖啡豆商品詳情頁 -->
<span class="title-bg-head">｛SERVED<br>&nbsp;&nbsp;&nbsp;FRESH｝</span>

<!-- 關於我們頁面 -->
<span class="title-bg-head">｛US｝</span>
```

**應用頁面**:
| 頁面 | 背景文字 | 語意 |
|------|----------|------|
| 咖啡詳情 (`coffee.html`) | `｛BREWED FAST｝` | 快速沖泡 |
| 咖啡豆詳情 (`bean.html`) | `｛SERVED FRESH｝` | 新鮮供應 |
| 關於我們 (`about.html`) | `｛US｝` | 品牌故事 |

### 2.5 設計語言
- 清晰且含空間感
- 簡潔留白但不失設計感
- 字體清晰可讀
- 背景層次豐富：SVG 插畫 + noise_animation 動畫 + 背景訊息字體
- 所有動畫僅限品牌已有的 `noise_animation`，不引入其他 CSS/JS 動畫
- 不使用漸變色（`linear-gradient`、`radial-gradient` 等）
- 功能優先，裝飾其次，不花巧

## 十三、UI 開發設計注意事項

### 13.1 核心原則
- **不花巧** — 功能優先，裝飾其次
- **無需動畫** — 避免不必要的 CSS/JS 動畫（品牌已有的 noise_animation 除外）
- **無需漸變色** — 使用純色，不使用 `linear-gradient`、`radial-gradient` 等

### 13.2 風格統一性
所有 UI 元素必須保持以下五個面向的統一：
1. **元素元件** — 卡片、按鈕、輸入框、列表等元件風格一致
2. **字體** — 嚴格遵循字型系統規範（Noto Serif TC / Noto Sans TC / Mogra）
3. **按鈕** — 統一使用 `.bc-btn` 系列樣式，不自行定義新按鈕風格
4. **色彩** — 嚴格使用品牌色系統中的顏色值，不引入新色
5. **圖標** — 優先使用 icomoon 字型圖標，不引入新圖標集

### 13.3 設計決策檢查清單
新增或修改 UI 元件前，請確認：
- [ ] 是否符合「輕鬆感、自由感、放空感」的品牌核心？
- [ ] 是否使用了品牌色系統中的顏色？
- [ ] 是否使用了規範中的字型？
- [ ] 是否與現有元件風格一致？
- [ ] 是否過於花巧？（如果是，簡化它）
- [ ] 是否真的需要動畫？（如果不需要，移除它）
- [ ] 是否使用了漸變色？（如果是，改用純色）

## 十四、UX 設計原則

### 14.1 設計主張

| 面向 | 主張 | 說明 |
|------|------|------|
| **使用者為中心** | 從使用者角度出發 | 每個設計決策都先問：使用者需要什麼？ |
| **功能優先** | 先有用，再好看 | 每個元件都必須有明確功能目的 |
| **減少認知負荷** | 不讓使用者思考 | 操作直覺、資訊清楚、回饋即時 |
| **一致性** | 一次學會，到處通用 | 同樣的操作模式在整個網站保持一致 |
| **包容性** | 為所有人設計 | 考慮不同裝置、網路速度、使用情境 |

### 14.2 體驗 (Experience)

> **核心問題**: 使用者在每個步驟的感受是什麼？

- **流暢度**: 操作路徑越短越好，減少不必要的步驟
- **回饋**: 每個操作都應有即時且明確的回饋（視覺變化、Toast 提示、狀態更新）
- **容錯**: 使用者犯錯時能輕鬆復原，不造成懲罰感
- **情緒**: 考慮使用者在不同階段的心理狀態（期待、焦急、滿意）

**範例 - 下單流程體驗**:
```
瀏覽商品 → 加入購物車 → 結帳 → 支付 → 等待製作 → 取餐
   😊          😊          🤔       😊       😐          😊
```
- 瀏覽商品：圖片清晰、描述簡潔、價格明確 → 輕鬆探索
- 加入購物車：一鍵加入、即時回饋 → 滿足感
- 結帳：資訊預填、步驟精簡 → 效率感
- 支付：多種選擇、安全提示 → 信任感
- 等待製作：即時狀態更新、排隊透明 → 降低焦慮
- 取餐：取餐碼清晰、通知即時 → 完成感

### 14.3 情境 (Context)

> **核心問題**: 使用者在什麼場景下使用這個功能？

- **實體環境**: 咖啡店內（吵雜/安靜）、路上（移動中）、家中（放鬆）
- **時間壓力**: 趕時間（快速下單）、悠閒（慢慢選）
- **裝置**: 手機（單手操作）、桌面（完整瀏覽）
- **網路**: 穩定（即時更新）、不穩定（離線降級）

**情境對照表**:

| 情境 | 使用者狀態 | 設計考量 |
|------|-----------|---------|
| 店內排隊點餐 | 趕時間、站著、單手操作 | 大按鈕、少步驟、快速加入 |
| 早上出門前預訂 | 匆忙、可能還沒清醒 | 歷史訂單一鍵復購、預設選項 |
| 下午茶悠閒時光 | 放鬆、有時間慢慢選 | 完整商品資訊、自定義選項 |
| 店內等候取餐 | 期待、可能有點無聊 | 即時狀態更新、排隊視覺化 |
| 晚上在家 | 放鬆、非急迫 | 瀏覽探索、咖啡知識內容 |

### 14.4 使用方式 (Usage)

> **核心問題**: 使用者如何完成他們的目標？

- **主要路徑**: 最常見的操作流程（下單 → 支付 → 取餐）
- **次要路徑**: 較少但重要的操作（查看歷史訂單、管理會員資料）
- **邊緣情況**: 不常見但需要處理的情況（支付失敗、取消訂單）

**主要使用路徑**:
```
首頁 → 選擇商品分類 → 加入購物車 → 結帳 → 選擇支付 → 完成
  ↓                                                        ↓
  可直接從導航列快速切換分類                             查看訂單狀態
```

**操作效率原則**:
- **3 次點擊規則**: 核心功能（加入購物車 → 結帳 → 支付）應在 3 次點擊內完成
- **預設值**: 提供合理的預設選項（如中杯、正常冰），減少選擇負擔
- **智慧預填**: 根據歷史記錄自動填入常用選項

### 14.5 效率 (Efficiency)

> **核心問題**: 如何讓使用者更快完成任務？

- **減少步驟**: 合併相關操作，移除不必要的確認步驟
- **快捷操作**: 常用功能提供快捷方式（如快速訂購、一鍵復購）
- **批次處理**: 允許一次完成多個操作（如一次加入多個商品）
- **預測**: 根據使用者行為預測下一步，提前準備

**效率提升策略**:

| 策略 | 實作方式 | 預期效益 |
|------|---------|---------|
| 一頁式結帳 | 商品確認、聯絡資訊、支付在同一頁 | 減少頁面跳轉 |
| 底部常駐購物車 | 隨時顯示數量與總價 | 降低購物車遺忘率 |
| 歷史訂單復購 | 一鍵複製上次訂單 | 提升回購效率 |
| 預設選項 | 根據熱門選擇預設 | 減少選擇時間 |
| 即時搜尋 | 輸入即過濾商品 | 快速找到目標商品 |

### 14.6 互動 (Interaction)

> **核心問題**: 使用者如何與系統互動？互動是否自然流暢？

- **即時性**: 操作後立即得到回應，避免無回應的等待
- **連續性**: 互動流程不中斷，狀態切換平滑
- **可預測性**: 使用者的操作能產生預期的結果
- **回饋豐富度**: 不同類型的操作給予不同層次的回饋（視覺、文字、狀態變化）

**互動模式對照**:

| 操作類型 | 回饋方式 | 範例 |
|---------|---------|------|
| 點擊按鈕 | 即時視覺變化 + 狀態文字 | 加入購物車按鈕變色 + Toast |
| 表單提交 | 載入動畫 + 成功/錯誤提示 | 結帳按鈕顯示 spinner |
| 狀態更新 | WebSocket 即時推送 | 訂單狀態從「準備中」→「已就緒」 |
| 錯誤操作 | 明確錯誤訊息 + 解決建議 | 電話格式錯誤提示 |

### 14.7 直覺 (Intuition)

> **核心問題**: 使用者不用說明書就能操作嗎？

- **心智模型**: 符合使用者對類似產品的既有認知（購物車 icon、結帳按鈕位置）
- **可見性**: 重要功能應該顯而易見，不需要尋找
- **映射**: 控制項與其效果的關係應該清楚（點擊加入 → 商品出現在購物車）
- **約束**: 限制錯誤操作的發生（不可選的選項灰色顯示）

**直覺設計檢查**:
- [ ] 購物車圖示是否在預期位置（右上角）？
- [ ] 點擊加入購物車是否有即時回饋？
- [ ] 結帳按鈕是否明顯且位置合理？
- [ ] 支付方式圖示是否易於辨識？
- [ ] 錯誤訊息是否告訴使用者如何修正？

## 十五、前後端無縫接合

> **核心問題**: 前端體驗與後端邏輯是否協調一致，使用者感受不到技術斷層？

### 15.1 即時狀態同步

- **WebSocket 連線**: 訂單狀態變化透過 WebSocket 即時推送，無需使用者手動刷新
- **連線狀態提示**: 當 WebSocket 斷線時顯示提示，重新連線後自動恢復
- **樂觀更新**: 使用者操作後先更新 UI，再等待後端確認，減少等待感

**即時更新場景**:

| 場景 | 觸發時機 | 前端行為 | 後端行為 |
|------|---------|---------|---------|
| 訂單狀態變更 | 員工操作 | 卡片動畫切換狀態 | 更新資料庫 + 發送 WS 事件 |
| 排佇列更新 | 新訂單加入 | 佇列視覺化更新 | 重新計算佇列 + 發送 WS 事件 |
| 購物車 badge | 加入/移除商品 | badge 數字動畫更新 | 更新 session/cart |
| 支付完成 | 支付平台回調 | 跳轉到確認頁面 | 更新訂單狀態 + 發送 WS 事件 |

### 15.2 表單提交與驗證

- **前端驗證**: 即時檢查輸入格式（電話、Email），減少後端拒絕
- **後端驗證**: 作為最終防線，返回明確的錯誤訊息
- **提交狀態**: 提交中顯示 loading 狀態，防止重複提交
- **錯誤恢復**: 提交失敗時保留已填寫的資料，不讓使用者重新輸入

**表單流程**:
```
使用者輸入 → 前端即時驗證（格式檢查）
                ↓
          通過 → 顯示提交按鈕可用
                ↓
          點擊提交 → 按鈕變為 loading 狀態（disabled + spinner）
                ↓
          後端驗證 → 成功 → 導航到下一步
                ↓
          失敗 → 顯示錯誤訊息 → 按鈕恢復可用
```

### 15.3 狀態一致性

- **單一資料源**: 前端顯示的狀態以後端回傳為準
- **狀態映射**: 後端狀態枚舉與前端顯示文字/顏色一一對應
- **過渡狀態**: 處理中間狀態（如「支付處理中」），避免顯示空白

**狀態映射表範例**:

| 後端狀態 | 前端顯示 | 顏色 | 圖示 |
|---------|---------|:----:|:----:|
| `pending` | 待處理 | 灰色 | ⏳ |
| `payment_pending` | 待支付 | 黃色 | 💳 |
| `paid` | 已支付 | 金色 | ✅ |
| `waiting` | 等待中 | 藍色 | ⏰ |
| `preparing` | 準備中 | 金色 | ☕ |
| `ready` | 已就緒 | 綠色 | 🔔 |
| `completed` | 已完成 | 灰色 | ✔️ |

### 15.4 錯誤處理與降級

- **網路錯誤**: 顯示友善的錯誤提示，提供重試選項
- **後端錯誤**: 顯示具體的錯誤原因，引導使用者下一步
- **降級方案**: 當 WebSocket 不可用時，自動降級為輪詢
- **資料持久化**: 使用者在填寫表單時，資料不會因意外而遺失

**錯誤處理層級**:

```
前端捕獲 → 網路錯誤 → Toast 提示 + 重試按鈕
         → 驗證錯誤 → 欄位下方即時提示
         → 業務錯誤 → Modal 或頁面提示

後端返回 → 400 → 顯示表單錯誤
         → 401 → 跳轉登入
         → 403 → 權限不足提示
         → 404 → 資源不存在提示
         → 500 → 系統錯誤提示 + 客服資訊
```

### 16.1 設計思考框架

當需要新增或修改 UI 元件時，依序思考以下問題：

  └── 使用者在什麼環境、什麼狀態下使用？

Step 3: 資訊架構
  └── 這個資訊/功能應該放在哪裡？

  └── 使用者如何與這個元素互動？

  └── 這個元素應該長什麼樣子？

## 十七、產出方案及策略關鍵

### 17.1 精確 (Precision)

> **核心問題**: 設計方案是否精確到可直接實作？

- **規格明確**: 每個元件的尺寸、顏色、間距、行為都有明確定義
- **狀態完整**: 涵蓋所有狀態（預設、懸浮、激活、禁用、載入、錯誤、空狀態）
- **邊界清晰**: 明確定義元件的邊界情況和極限值
- **程式碼對應**: 設計規格與 CSS 變數、元件 class 一一對應

**精確度檢查**:
- [ ] 是否有明確的尺寸規格（px/rem）？
- [ ] 是否有明確的顏色值（hex/rgb/var）？
- [ ] 是否有明確的行為描述（點擊、hover、過渡）？
- [ ] 是否涵蓋了所有狀態？
- [ ] 是否考慮了邊界情況？

### 17.2 品牌一致性 (Brand Consistency)

> **核心問題**: 設計方案是否維持品牌識別的一致性？

- **元件一致性**: 使用現有元件庫，不重複發明
- **色彩一致性**: 嚴格使用品牌色系統，不引入新色
- **字型一致性**: 嚴格遵循字型系統規範
- **圖標一致性**: 優先使用 icomoon 字型圖標
- **語氣一致性**: 所有文字內容符合品牌調性（輕鬆、自由、放空）

**品牌一致性檢查**:
- [ ] 是否使用了 `.bc-btn` 系列按鈕？
- [ ] 是否使用了品牌色系統中的顏色？
- [ ] 是否使用了規範中的字型？
- [ ] 是否使用了 icomoon 圖標？
- [ ] 文字語氣是否符合品牌調性？

### 17.3 設計品質 (Design Quality)

> **核心問題**: 設計方案是否達到足夠的品質水準？

- **細節打磨**: 關注微互動、過渡動畫、間距微調等細節
- **邊緣情況**: 處理載入中、空狀態、錯誤狀態、極限情況
- **效能考量**: 避免過多的 DOM 操作、不必要的動畫、大型圖片
- **可訪問性**: 考慮色彩對比度、字型大小、鍵盤導航
- **一致性**: 與現有設計語言保持一致

**品質檢查**:
- [ ] 載入狀態是否有 skeleton 或 spinner？
- [ ] 空狀態是否有引導使用者操作的提示？
- [ ] 錯誤狀態是否有明確的解決方案？
- [ ] 動畫是否流暢（60fps）？
- [ ] 色彩對比度是否足夠（WCAG AA 標準）？
- [ ] 是否支援鍵盤操作（Tab、Enter、Escape）？

## 十八、常見場景設計指引

### 18.1 商品瀏覽與選擇

**UX 考量**:
- 使用者可能不確定要喝什麼 → 提供分類瀏覽和熱門推薦
- 選擇選項（冰量、甜度）可能造成困擾 → 提供預設值
- 商品描述太長會影響瀏覽效率 → 三行截斷

**UI 指引**:
- 商品卡片使用統一的 `.bc-product-card` 樣式
- 圖片使用去背 PNG，無背景色
- 名稱、價格、選項按鈕的視覺層級清晰
- 描述文字最多三行，超出顯示「...」

### 18.2 購物車操作

**UX 考量**:
- 使用者希望不離開當前頁面就能管理購物車 → 滑出抽屜
- 需要清楚知道購物車內容和總價 → 底部常駐資訊
- 可能改變心意移除商品 → 一鍵移除

**UI 指引**:
- 滑出購物車從右側滑入，不遮蓋主要內容
- 商品列表可滾動，底部固定顯示總價和操作按鈕
- 空狀態顯示購物車圖示和「來一杯咖啡吧」

### 18.3 結帳流程

**UX 考量**:
- 步驟越少越好 → 一頁式結帳
- 聯絡資訊應盡量預填 → 從會員資料自動帶入
- 支付方式選擇應直覺 → 圖示 + 名稱

**UI 指引**:
- 區塊式佈局：訂單商品 → 聯絡資訊 → 取貨時間 → 支付方式 → 摘要
- 每個區塊有對應圖示
- 支付選項使用大圖示 + 名稱，易於辨識

### 18.4 訂單狀態追蹤

**UX 考量**:
- 等待是痛苦的 → 即時狀態更新降低焦慮
- 想知道還要等多久 → 排隊位置和預計時間
- 取餐時需要辨識資訊 → 取餐碼

**UI 指引**:
- 狀態變化透過 WebSocket 即時更新
- 狀態文字和顏色清楚對應（等待中、準備中、已就緒）
- 取餐碼大字顯示，方便店員辨識

### 18.5 錯誤與邊緣情況

**UX 考量**:
- 支付失敗時不驚慌 → 清楚說明原因和解決方式
- 網路不穩定時不遺失資料 → 本地暫存
- 操作錯誤時能復原 → 提供取消/返回選項

**UI 指引**:
- 錯誤訊息使用 Toast 顯示，不中斷操作
- 錯誤說明使用平實語言，不顯示技術錯誤碼
- 提供明確的下一步操作建議

## 十九、設計審查檢查清單

### 19.1 UX 審查

- [ ] **使用者目標**: 這個設計是否幫助使用者達成目標？
- [ ] **操作路徑**: 完成核心任務需要多少步驟？能否減少？
- [ ] **回饋**: 每個操作是否有即時回饋？
- [ ] **容錯**: 使用者犯錯時能否輕鬆復原？
- [ ] **學習成本**: 新使用者需要多久才能上手？
- [ ] **效率**: 常用操作是否夠快？
- [ ] **情境**: 是否考慮了不同的使用情境？
- [ ] **邊緣情況**: 是否處理了錯誤和邊緣情況？

### 19.2 UI 審查

- [ ] **品牌一致性**: 是否符合品牌色、字型、元件規範？
- [ ] **視覺層級**: 資訊層級是否清楚？
- [ ] **可讀性**: 文字大小和對比度是否足夠？
- [ ] **可點擊性**: 可互動元素是否有清楚的視覺提示？
- [ ] **狀態**: 所有狀態（預設、懸浮、激活、禁用）是否都有定義？
- [ ] **響應式**: 在不同螢幕尺寸上是否正常顯示？
- [ ] **觸控**: 觸控目標是否夠大？
- [ ] **動畫**: 動畫是否有意義？是否克制使用？

### 19.3 前後端接合審查

- [ ] **即時更新**: 狀態變化是否透過 WebSocket 即時推送？
- [ ] **表單提交**: 提交中是否有 loading 狀態？失敗是否保留資料？
- [ ] **狀態同步**: 前端顯示的狀態是否與後端一致？
- [ ] **錯誤處理**: 網路錯誤、後端錯誤是否有友善提示？
- [ ] **降級方案**: WebSocket 不可用時是否有替代方案？
- [ ] **資料持久化**: 使用者的輸入資料是否不會意外遺失？

### 19.4 最終檢查

- [ ] 是否符合「輕鬆感、自由感、放空感」的品牌核心？
- [ ] 是否使用了品牌色系統中的顏色？
- [ ] 是否使用了規範中的字型？
- [ ] 是否與現有元件風格一致？
- [ ] 是否過於花巧？（如果是，簡化它）
- [ ] 是否真的需要動畫？（如果不需要，移除它）
- [ ] 是否使用了漸變色？（如果是，改用純色）
- [ ] 是否考慮了手機和桌面的不同體驗？
- [ ] 是否處理了載入中、空狀態、錯誤狀態？
- [ ] 是否考慮了前後端資料流的一致性？

## 附錄 B: 快速參考

### 設計決策檢查流程

```
收到設計需求
    ↓
1. 分析使用者需求與情境
    ↓
2. 四角色分析（工程師/前端/設計師/用戶）
    ↓
3. 參考現有元件庫，確保一致性
    ↓
4. 考慮前後端接合方式
    ↓
5. 設計方案
    ↓
6. 對照審查檢查清單
    ↓
7. 實作
    ↓
8. 驗證（不同裝置、不同情境）
```

### 常見設計陷阱

| 陷阱 | 解決方式 |
|------|---------|
| 過度設計 | 問自己：這個元素真的需要嗎？ |
| 忽略手機 | 先設計手機版，再擴展到桌面 |
| 不一致 | 建立並遵循元件庫 |
| 忽略回饋 | 每個操作都加上視覺回饋 |
| 過多動畫 | 只保留對使用者有幫助的動畫 |
| 前後端脫節 | 設計時同步考慮 API 請求和狀態同步 |
| 忽略邊緣情況 | 列出所有可能的狀態並逐一處理 |
