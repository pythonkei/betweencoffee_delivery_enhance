# `.clinerules` 配置與使用指南

## 行為變化示例

### 1. Plan Mode 行為變化
**配置前**:
- 直接開始實施任務
- 缺乏系統狀態分析

**配置後**:
- 先分析現有系統狀態
- 參考「綜合工作總結與遷移報告.md」
- 制定詳細實施計劃
- 識別潛在風險和挑戰

### 2. Act Mode 行為變化
**配置前**:
- 可能進行大規模修改
- 測試不夠充分

**配置後**:
- 使用增量修改策略
- 每次修改後進行測試
- 遵循測試驅動開發原則
- 更新相關文檔

### 3. 代碼質量變化
**配置前**:
- 文檔可能不完整
- 函數可能沒有明確返回值

**配置後**:
- 所有新函數必須附帶詳細文檔
- 函數必須有明確的回傳值
- 遵循單一職責原則

### 4. 安全意識變化
**配置前**:
- 可能忽略安全檢查

**配置後**:
- WebSocket 連接必須經過身份驗證
- 敏感數據必須加密存儲
- 所有用戶輸入必須進行驗證

## 自訂規則示例

### 添加新規則
在 `.clinerules` 文件中添加新的規則部分：

```markdown
## 新功能開發規範
1. **需求分析**:
   - 必須先分析現有架構兼容性
   - 必須評估對現有功能的影響

2. **實現要求**:
   - 必須提供 API 文檔
   - 必須包含單元測試和集成測試

3. **部署要求**:
   - 必須通過所有測試
   - 必須有回滾計劃
```

### 修改現有規則
編輯 `.clinerules` 文件中的相應部分：

```markdown
### 測試要求
- 所有新增功能必須覆蓋至少 **90%** 的單元測試（原為 80%）
- 關鍵業務邏輯必須有 **端到端測試**
- 測試用例必須包含 **性能測試**
```

### 情境化規則
可以根據任務類型添加情境化規則：

```markdown
## 任務類型特定規則
### [BUGFIX]
- 優先分析問題根源
- 創建最小重現案例
- 實施修復並測試邊界情況

### [FEATURE]
- 分析現有架構兼容性
- 設計增量實現方案
- 確保向後兼容
```

## 最佳實踐

### 1. 規則設計原則
- **具體明確**: 避免模糊的指導原則
- **可驗證**: 規則應該可以被測試驗證
- **可執行**: Cline 能夠理解和執行規則
- **一致性**: 與現有開發流程保持一致

### 2. 維護建議
- **定期更新**: 隨著項目發展更新規則
- **版本控制**: 將 `.clinerules` 納入版本控制
- **團隊協作**: 確保團隊成員了解規則
- **文檔同步**: 更新相關技術文檔

### 3. 測試策略
- **自動化測試**: 使用測試腳本驗證規則
- **手動驗證**: 定期檢查 Cline 行為是否符合預期
- **回饋機制**: 收集使用回饋並改進規則

## 故障排除

### 常見問題

#### 問題 1: Cline 沒有遵循規則
**解決方案**:
1. 檢查 `.clinerules` 文件是否存在於項目根目錄
2. 驗證文件格式是否正確
3. 重啟 Cline 或重新加載項目

#### 問題 2: 規則衝突
**解決方案**:
1. 檢查規則之間的一致性
2. 優先級高的規則覆蓋優先級低的規則
3. 重新組織規則結構

#### 問題 3: 規則過於嚴格
**解決方案**:
1. 調整規則的嚴格程度
2. 添加例外情況說明
3. 使用情境化規則

